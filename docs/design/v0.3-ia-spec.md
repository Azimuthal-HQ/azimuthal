## 0. How to use this document

This is the authoritative design input for the v0.3 line. Everything here is a constraint,
not a suggestion.

Section 2 governs the rest of the document. Every phase in section 9 is gated on it. If a
phase's feature work is complete but its testing obligations are not, the phase is not
complete.

There are no open decisions. If implementation surfaces a genuine ambiguity, stop and raise
it in the PR body — do not resolve it unilaterally and do not infer intent from surrounding
code.

Where this document conflicts with an older doc, this document wins and the older doc is
flagged for update in the PR body. Never silently edit around a conflict.

## 1. Scope and non-goals

### In scope for v0.3

- Persistent navigation shell with the product switcher in the top bar
- Full Beacon / Codex / Vector rebrand, including the database representation
- Teams as a first-class grouping concept, nested to a maximum of five levels
- Explicit space grants with subject-side team expansion
- Capability-based permission checks
- Per-entity org-wide and team-wide shares — read-only, widening only, optionally expiring
- Space directory with visibility levels
- Saved views as the query substrate
- Dashboards and a gadget registry
- Cross-module search on PostgreSQL full-text
- Audit logging for teams, grants, and shares

### Explicit non-goals for v0.3

- Third-party or user-authored gadgets — the registry seam is built now, hosting and
  sandboxing deferred
- Aggregate-only visibility — the capability model accommodates it, implementation deferred
- Request-access workflows — the directory ships with "contact a space admin" only
- Share notifications
- SCIM or OIDC group sync — `source` columns exist now so adding sync later is not a
  migration on live data
- Mobile and responsive work beyond not breaking existing layouts
- Managed hosting, billing, or any pricing-tier concept. **No revenue model, hosting tier,
  or paywall language belongs anywhere in the codebase or documentation.**

## 2. Testing — the governing discipline

**This section overrides any instruction that would reduce coverage, weaken an assertion,
or defer test work to a later PR.**

### 2.1 Why this section exists

Releases v0.1.0 through v0.1.14 were almost entirely regression repair. It was never a
shortage of tests in absolute terms — it was tests that never exercised the thing that
broke:

- Build, lint, and unit tests passed while real database operations failed
- Playwright specs were skipped for "known gaps" instead of failing loudly
- Frontend-to-backend URL and casing mismatches shipped because no test crossed the boundary
- Signing keys regenerated on restart, invalidating every JWT, with no test covering restart

Every rule below exists because one of those cost a release.

### 2.2 The blast-radius rule

**Any PR that adds, changes, or removes behaviour must update the tests inside that
behaviour and the tests around it.** "Around it" is not a judgement call. The PR body must
state what was checked for each row:

| Surface | What must be re-examined |
|---|---|
| Direct callers | Every function or component invoking the changed code |
| Direct callees | Every contract the changed code depends on |
| Sibling routes | Any route sharing a handler, middleware, layout, or component |
| The E2E journey | Every Playwright spec whose path traverses the change |
| The API contract | OpenAPI regenerated via `make docs`, committed in the same PR |
| Permissions | Section 2.5, if the change touches reads, writes, or scoping |
| Fixtures | Any fixture whose shape the change invalidates |

A PR that changes a handler and updates only that handler's own test is incomplete, even
with green CI.

### 2.3 Test debt is not permitted

- No PR merges with "tests to follow." There is no follow-up PR.
- No feature is done with an untested path. If a path cannot be tested, the PR stays DRAFT
  and says why, per item.
- **Assertions are never weakened.** Not to make a test pass, not to unblock a merge, not
  under any framing, not if a prompt instructs it. A failing test means either the code is
  wrong or the test encodes a requirement worth discussing. Never a third thing.

### 2.4 Deletion and skip discipline

**Removing a feature means removing its tests**, not skipping them.

A skipped test is permitted only with all three of:

1. A `SKIP:` comment naming the specific blocker
2. A referenced GitHub issue number
3. A stated condition under which it will be re-enabled

CI fails on any skip lacking these.

### 2.5 Mandatory test matrix — permissions

Any PR touching teams, grants, shares, space visibility, or any read path must cover every
case. A missing case is a failing review.

| # | Case | Expected |
|---|---|---|
| 1 | Direct user grant on a space | Access at granted role |
| 2 | Grant to the user's own team | Access at granted role |
| 3 | Grant to a team **below** the user's team | Access — subject-side expansion |
| 4 | Grant to a team **above** the user's team | **No access** |
| 5 | Grant to a sibling team | **No access** |
| 6 | User in two teams with different roles on one space | Highest role wins |
| 7 | Org admin with zero grant rows | Full access via middleware bypass |
| 8 | Space `visibility = 'org'` | Every org member reads, no grant needed |
| 9 | Space `visibility = 'hidden'` | Absent from directory for non-grantees |
| 10 | Space `visibility = 'discoverable'` | Listed but unreadable for non-grantees |
| 11 | Entity share, audience org | Entity readable, space still not |
| 12 | Entity share with cascade | Descendant pages readable |
| 13 | Entity share revoked | Access removed on the next request |
| 14 | Entity share past `expires_at` | Access removed, no sweeper required |
| 15 | Shared entity | Read only — write attempts rejected |
| 16 | Shared entity | Container, tree, siblings, and comments remain hidden |
| 17 | Shared entity moved to another space | All its shares revoked |
| 18 | Shared entity deleted | All its shares revoked in the same transaction |
| 19 | Team reparent exceeding depth 5 | Rejected |
| 20 | Team parent cycle | Rejected |
| 21 | Grant to a non-org-member | Rejected, 400 |
| 22 | User deleted | Their grants removed in the same transaction |
| 23 | List endpoint, N results | Constant number of authorisation queries |

Case 23 is a performance assertion and it is mandatory. A list endpoint issuing one
authorisation query per row is a defect regardless of output correctness.

### 2.6 Mandatory test matrix — every new endpoint

| Case | Expected |
|---|---|
| No credentials | 401 |
| Valid credentials, no access | 404 — never 403, do not leak existence |
| Valid credentials, wrong capability | 403 |
| Happy path | 2xx with correct body |
| Missing required field | 400 with the documented error shape |
| Wrong field type | 400 with the documented error shape |
| Wire format | Response keys are lowercase snake_case |
| Pagination, if a list | Cursor behaviour at first, middle, and empty pages |

### 2.7 Regression tests for defects

Every fixed defect gets a test that **fails before the fix and passes after**. State that
you verified both directions. Name it for the defect, not the function —
`TestSprintCreate_RejectsSnakeCaseMismatch_Regression`, not `TestSprintCreate2`.

### 2.8 Layers and commands

```bash
make test-db-up      # postgres :5433, minio :9001
go build ./...
go vet ./...
make test-live       # Go integration tests against real postgres
make verify-api      # API smoke checks
make e2e-test        # Playwright
make test-db-down
```

**Real PostgreSQL only**, via `internal/testutil.NewTestDB(t)`. No mocks exist, none will
be added. Mocks hide constraint violations and casing bugs — both shipped in v0.1.x.

Coverage gate is 80%, rising to 85% at the end of P5. Coverage is a floor, not a goal; case
23 above is worth more than five percentage points.

### 2.9 PR gate

All three of `make test-live`, `make verify-api`, and `make e2e-test` exit 0, or the PR is
**DRAFT** with a per-item reason. Every test plan item is either checked with its
verification method stated, or unchecked with an explicit explanation. **Never a blank
checkbox.**

No release tag without `make regression-test` and `make e2e-test` both passing.

**What went wrong, so it does not go wrong a fourth time.** Three failures, three causes:

- **The first version was wrong the day it was published.** It numbered the sequence `006`–`012`
  while `020_drop_org_plan.sql` was already on disk — a base fifteen migrations stale. Nobody had
  read the directory. P1.5 caught it (D1, D2), and `021_space_type_rebrand.sql` records the
  correction in-file.
- **The second version was correct when written and decayed.** P1.5 renumbered to `021`–`027`
  accurately. Two days later P2.5 — a phase nowhere in this document's plan, which §9 now records
  only in hindsight — took `024` and `025`, pushing entity shares to `026`; P3 then needed `027`
  for attachments. Every number assigned to P4, P5 and P6 was consumed by phases that shipped in
  between.

- **The third version decayed the same way, faster.** P1.5's correction said `029` was next free
  and it was, for a while. Seven migrations then shipped from phases this document does not plan —
  two post-P3 stabilisation fixes, three for Vector completion, two for Vector surfaces — so by
  the time the Codex editor phase read this table it was seven numbers stale and claimed a number
  that had been taken months earlier. The rows above are now filled in from the directory rather
  than from the plan.

So the table can be wrong because nobody checked the directory, **and** it can be wrong because
the directory moved after someone checked. Only reading `migrations/` at the moment you assign a
number defends against both. The pattern is now established beyond argument: **the shipped rows of
this table are a record and the unassigned rows are a guess, and the guess has been wrong every
single time it has been tested.**

`037` is the next free number *as of migration 036*. Beyond that, only the *ordering* is fixed,
not the allocation: a phase taking two migrations shifts everything after it. Read the directory,
never this table, before choosing a number.

### 021_space_type_rebrand.sql — shipped in P1

The rebrand is complete, including the database representation. What follows is the
migration as it shipped, verbatim. Three facts differ from this document's earlier sketch,
each verified against the repository and a live database before the migration was written:
the old literal is `service_desk` (not `servicedesk`); the pre-existing constraint is the
auto-named inline CHECK `spaces_type_check` from `003_spaces.sql` (not `spaces_type_valid`);
and the down migration must restore that original constraint, which the earlier sketch
omitted — a rollback would have left the column unconstrained.

```sql
-- +goose Up
-- +goose StatementBegin

-- Space type rebrand (v0.3 spec §4, migration "006" in the spec's table —
-- numbered 021 here because the shipped scaffold already ends at 020):
-- service_desk → beacon, wiki → codex, project → vector.
-- spaces_type_check is the auto-generated name of the inline CHECK from
-- 003_spaces.sql, confirmed against pg_constraint on a live database.
ALTER TABLE spaces DROP CONSTRAINT IF EXISTS spaces_type_check;

UPDATE spaces SET type = CASE type
    WHEN 'service_desk' THEN 'beacon'
    WHEN 'wiki'         THEN 'codex'
    WHEN 'project'      THEN 'vector'
    ELSE type
END;

ALTER TABLE spaces ADD CONSTRAINT spaces_type_valid
    CHECK (type IN ('beacon', 'codex', 'vector'));

-- +goose StatementEnd

-- +goose Down
-- +goose StatementBegin

ALTER TABLE spaces DROP CONSTRAINT spaces_type_valid;

UPDATE spaces SET type = CASE type
    WHEN 'beacon' THEN 'service_desk'
    WHEN 'codex'  THEN 'wiki'
    WHEN 'vector' THEN 'project'
    ELSE type
END;

-- Restore the original constraint under its original auto-generated name so
-- a down migration returns the schema to the exact post-020 state.
ALTER TABLE spaces ADD CONSTRAINT spaces_type_check
    CHECK (type IN ('project', 'wiki', 'service_desk'));

-- +goose StatementEnd
```

**This migration had an unusually large blast radius.** It touched sqlc queries, handlers,
frontend types, API responses, the OpenAPI spec, fixtures, and E2E selectors. Section 2.2
applied with full force; the grep gate over the three old literals was run and recorded in
PR #51.

### 022_teams.sql

Teams use a materialised path by ID, consistent with the Codex page hierarchy. Descendant
expansion becomes a single indexed query, and the depth limit becomes a database constraint
rather than application trust.

```sql
-- +goose Up
CREATE TABLE teams (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id      UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    parent_id   UUID REFERENCES teams(id) ON DELETE RESTRICT,
    path        UUID[] NOT NULL,
    slug        TEXT NOT NULL,
    name        TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    is_default  BOOLEAN NOT NULL DEFAULT false,
    source      TEXT NOT NULL DEFAULT 'manual',
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at  TIMESTAMPTZ,
    UNIQUE (org_id, slug),
    CONSTRAINT teams_depth_max      CHECK (array_length(path, 1) BETWEEN 1 AND 5),
    CONSTRAINT teams_path_ends_self CHECK (path[array_length(path, 1)] = id),
    CONSTRAINT teams_source_valid   CHECK (source IN ('manual','scim','oidc'))
);

CREATE INDEX teams_path_gin ON teams USING GIN (path);
CREATE INDEX teams_org_idx  ON teams (org_id) WHERE deleted_at IS NULL;
CREATE UNIQUE INDEX teams_one_default ON teams (org_id)
    WHERE is_default AND deleted_at IS NULL;

CREATE TABLE team_members (
    team_id    UUID NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
    user_id    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    org_id     UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    role       TEXT NOT NULL DEFAULT 'member',
    is_primary BOOLEAN NOT NULL DEFAULT false,
    source     TEXT NOT NULL DEFAULT 'manual',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (team_id, user_id),
    CONSTRAINT team_members_role_valid   CHECK (role   IN ('member','lead')),
    CONSTRAINT team_members_source_valid CHECK (source IN ('manual','scim','oidc'))
);

CREATE UNIQUE INDEX team_members_one_primary ON team_members (user_id, org_id)
    WHERE is_primary;
CREATE INDEX team_members_user_idx ON team_members (user_id, org_id);

-- +goose Down
DROP TABLE team_members;
DROP TABLE teams;
```

The scaffold **already has an `audit_log` table** — `008_audit_log.sql` — so this migration
does **not** create one. The existing schema differs from this document's earlier sketch and
is what P2's audit events must write to:

```sql
-- Existing table, created by 008_audit_log.sql. Shown for reference — do not recreate.
CREATE TABLE audit_log (
    id           UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id       UUID        NOT NULL REFERENCES organizations (id),
    actor_id     UUID        REFERENCES users (id),
    action       TEXT        NOT NULL,
    entity_kind  TEXT        NOT NULL,   -- earlier sketch said entity_type, nullable
    entity_id    UUID        NOT NULL,   -- earlier sketch had this nullable
    payload      JSONB       NOT NULL DEFAULT '{}',   -- earlier sketch said metadata
    ip_address   INET,
    user_agent   TEXT,                   -- not in the earlier sketch
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
-- Existing indexes: idx_audit_log_org_id (org_id, created_at DESC),
-- idx_audit_log_actor_id (actor_id) WHERE actor_id IS NOT NULL,
-- idx_audit_log_entity (entity_kind, entity_id).
```

Note `entity_kind` and `entity_id` are NOT NULL — every audit event must name an entity,
which every event in section 6's list does.

**Append-only. Never UPDATE, never DELETE.**

**Store-layer obligations, each with a test:**

- `path` is always constructed as `parent.path || id`. Never hand-assembled.
- Reparenting rewrites the paths of the moved node and all descendants in one transaction.
- Reparenting checks `depth(new_parent) + height(moved_subtree) ≤ 5` **before** the move.
  Checking only the moved node's own depth is insufficient and is the case most likely to be
  missed.
- A parent assignment creating a cycle is rejected — verify `id` is absent from the
  prospective parent's path.
- Deleting a team: `RESTRICT` if it has children or owns spaces. Members move to the org
  default team; if it was someone's primary, the default becomes primary.
- New users join the org default team with `is_primary = true`.
- Team slug is unique per org. Two teams named "Design" under different parents need
  different slugs.

### 023_space_grants.sql

```sql
-- +goose Up
CREATE TABLE space_grants (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id       UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    space_id     UUID NOT NULL REFERENCES spaces(id) ON DELETE CASCADE,
    subject_type TEXT NOT NULL,
    subject_id   UUID NOT NULL,
    role         TEXT NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    created_by   UUID REFERENCES users(id),
    UNIQUE (space_id, subject_type, subject_id),
    CONSTRAINT space_grants_subject_valid CHECK (subject_type IN ('user','team')),
    CONSTRAINT space_grants_role_valid
        CHECK (role IN ('viewer','contributor','agent','space_admin'))
);

CREATE INDEX space_grants_space_idx   ON space_grants (space_id);
CREATE INDEX space_grants_subject_idx ON space_grants (subject_type, subject_id);

ALTER TABLE spaces ADD COLUMN owner_team_id UUID REFERENCES teams(id) ON DELETE RESTRICT;
ALTER TABLE spaces ADD COLUMN visibility TEXT NOT NULL DEFAULT 'discoverable';

UPDATE spaces s SET owner_team_id = (
    SELECT t.id FROM teams t WHERE t.org_id = s.org_id AND t.is_default LIMIT 1
) WHERE owner_team_id IS NULL;

ALTER TABLE spaces ALTER COLUMN owner_team_id SET NOT NULL;
ALTER TABLE spaces ADD CONSTRAINT spaces_visibility_valid
    CHECK (visibility IN ('hidden','discoverable','org'));

CREATE INDEX spaces_owner_team_idx ON spaces (owner_team_id) WHERE deleted_at IS NULL;

-- +goose Down
ALTER TABLE spaces DROP CONSTRAINT spaces_visibility_valid;
ALTER TABLE spaces DROP COLUMN visibility;
ALTER TABLE spaces DROP COLUMN owner_team_id;
DROP TABLE space_grants;
```

**Space visibility levels.** One column answers two questions:

| Value | In directory | Readable without a grant |
|---|---|---|
| `hidden` | No | No |
| `discoverable` | Yes, as a locked row with "contact a space admin" | No |
| `org` | Yes | Yes, at `viewer` |

`owner_team_id` is required. It grants nothing by itself — it drives picker grouping and
guarantees no orphaned space. Reachability is guaranteed by the org-admin middleware bypass,
**not** by a second permission path such as an admins team.

**Referential obligations, each with a test.** `subject_id` is polymorphic and has no foreign
key, so integrity is the store layer's responsibility:

- Deleting a user deletes their grants in the same transaction.
- A grant to a user who is not a member of the org is rejected with 400.

### 026_entity_shares.sql — shipped in P3

Shipped as `026`, not the `024` this document originally sketched: P2.5 took 024–025 while this
section still read `024`. The table below is the migration **as it shipped**. Columns and all
five constraint names match the original sketch exactly; the shipped migration adds one index the
sketch did not have — `entity_shares_org_idx` — because the per-request resolution query and the
org share listing both filter on `org_id` first, and without it every resolution full-scans once
several orgs share an instance.

```sql
-- +goose Up
CREATE TABLE entity_shares (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id      UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    space_id    UUID NOT NULL REFERENCES spaces(id) ON DELETE CASCADE,
    entity_type TEXT NOT NULL,
    entity_id   UUID NOT NULL,
    audience    TEXT NOT NULL,
    audience_id UUID REFERENCES teams(id) ON DELETE CASCADE,
    cascade     BOOLEAN NOT NULL DEFAULT false,
    expires_at  TIMESTAMPTZ,
    created_by  UUID NOT NULL REFERENCES users(id),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    revoked_at  TIMESTAMPTZ,
    CONSTRAINT entity_shares_type_valid
        CHECK (entity_type IN ('page','ticket','project_item')),
    CONSTRAINT entity_shares_audience_valid CHECK (audience IN ('org','team')),
    CONSTRAINT entity_shares_audience_id_present
        CHECK ((audience = 'team') = (audience_id IS NOT NULL)),
    CONSTRAINT entity_shares_cascade_pages_only
        CHECK (cascade = false OR entity_type = 'page'),
    CONSTRAINT entity_shares_expiry_future
        CHECK (expires_at IS NULL OR expires_at > created_at)
);

CREATE UNIQUE INDEX entity_shares_unique_active
    ON entity_shares (entity_type, entity_id, audience,
                      COALESCE(audience_id, '00000000-0000-0000-0000-000000000000'::uuid))
    WHERE revoked_at IS NULL;

CREATE INDEX entity_shares_entity_idx   ON entity_shares (entity_type, entity_id)
    WHERE revoked_at IS NULL;
CREATE INDEX entity_shares_audience_idx ON entity_shares (audience, audience_id)
    WHERE revoked_at IS NULL;
CREATE INDEX entity_shares_expiry_idx   ON entity_shares (expires_at)
    WHERE revoked_at IS NULL AND expires_at IS NOT NULL;
CREATE INDEX entity_shares_org_idx ON entity_shares (org_id)
    WHERE revoked_at IS NULL;

-- +goose Down
DROP TABLE entity_shares;
```

Revocation sets `revoked_at`; rows are never hard-deleted, so the audit trail survives.
Expiry is evaluated in the resolution query — a share past `expires_at` stops granting access
on the next request, with no sweeper involved. A nightly job may mark expired rows for
tidiness, but access must never depend on it.

There is deliberately **no foreign key on `(entity_type, entity_id)`** — the pair is polymorphic
and the store layer owns its integrity, which is why revoke-on-delete and revoke-on-move must run
in the same transaction as the entity mutation.

### 027_attachments.sql — shipped in P3

**This table is new to this document.** It shipped in P3 and nothing here planned for it. It is
a first-class part of the schema.

Attachments exist because of ADR-0008 rule 3 — "attachments follow the entity". A page shared
org-wide must render its images for a viewer with no space access, and until P3 the `ObjectStore`
had no production caller at all (known-issue #16, now closed). The shared read path forced the
issue, and it had to be closed without turning that path into a way to fetch arbitrary object
keys.

```sql
-- +goose Up
CREATE TABLE attachments (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id       UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
    entity_type  TEXT NOT NULL,
    entity_id    UUID NOT NULL,
    filename     TEXT NOT NULL,
    content_type TEXT NOT NULL,
    size_bytes   BIGINT NOT NULL,
    object_key   TEXT NOT NULL,
    created_by   UUID NOT NULL REFERENCES users(id),
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    deleted_at   TIMESTAMPTZ,
    CONSTRAINT attachments_type_valid
        CHECK (entity_type IN ('page','ticket','project_item')),
    CONSTRAINT attachments_filename_present CHECK (length(filename) > 0),
    CONSTRAINT attachments_size_nonnegative CHECK (size_bytes >= 0),
    CONSTRAINT attachments_object_key_unique UNIQUE (object_key)
);

CREATE INDEX attachments_entity_idx ON attachments (entity_type, entity_id)
    WHERE deleted_at IS NULL;

-- +goose Down
DROP TABLE attachments;
```

Two design choices are load-bearing and must not be "simplified" away:

- **The object key is never accepted from the client.** It is computed once at upload as
  `orgs/{org_id}/attachments/{id}` — org-prefixed so a bucket policy can scope by tenant,
  id-suffixed so it is unguessable — persisted into `object_key`, and every read looks the
  attachment up by id under its entity and uses the key **stored on the row**. A read path that
  took a key parameter would be an arbitrary-object-read primitive reachable by anyone holding any
  share. There is a test for this.
- **There is no `space_id` column, on purpose.** Authorisation always derives from the entity the
  attachment hangs off, so a cross-space entity move cannot strand a stale container reference
  here. This is the same reasoning that makes shares revoke on move.

`(entity_type, entity_id)` is polymorphic with no FK and carries the same three-value vocabulary
as `entity_shares`. It is enforced twice: as a DB CHECK on each table (`attachments_type_valid`,
`entity_shares_type_valid`) and in Go by `access.ValidShareEntityType`. Deletion is soft
(`deleted_at`); no hard-delete query exists.

### 028_space_slug_per_module.sql — shipped after P3

Space slug uniqueness moved from `(org_id, slug)` to `(org_id, type, slug)`, so one org can hold
a Beacon desk, a Codex wiki and a Vector board all slugged `devops`. It drops
`spaces_org_id_slug_key` — the auto-generated name of the inline `UNIQUE (org_id, slug)` from
`003_spaces.sql`, confirmed against `pg_constraint` the same way `021` confirmed
`spaces_type_check` — and adds `spaces_org_id_type_slug_key`.

Like the constraint it replaces it is deliberately **not** partial on `deleted_at`: a
soft-deleted space keeps holding its slug within its module.

Its down migration **fails by design** on any database where a slug now exists in more than one
module, rather than silently renaming or dropping someone's space.

Note that `idx_spaces_org_key` from `017_space_key.sql` — the unique index on `(org_id, key)` —
was **not** changed and remains org-wide. Space *keys* still collide across modules even though
slugs no longer do.

### 038_saved_views.sql — shipped in P4

**Superseded by what shipped.** The sketch below is kept for the record; read
`migrations/038_saved_views.sql` for the table that exists. It was numbered 029 here and shipped
as 038 — the fourth time this table's number went stale (**D56**).

Three parts of the sketch were NOT implemented, and each is a correction rather than a preference
(**D57**, **D58**, and the decision note in the P4 section of
`spec-repo-reconciliation.md`):

- `visibility_team_id ... ON DELETE CASCADE` **deletes the saved view** when its audience team is
  deleted, and the accompanying CHECK makes nulling the column a constraint violation instead.
  Both contradict ADR-0009's own decision-log case C1, which requires the view to survive, be
  marked invalid and prompt its owner. Shipped as `ON DELETE SET NULL` with no CHECK, the
  invariant enforced on the write path.
- `is_valid` needs a writer nothing in the design provides. Validity is derived at read time, in
  one query for a whole page of views.
- The `{field, op, value}` query JSON below is a query language. What shipped is a closed record of
  named fields — see the correction after the sketch.

The module vocabulary also differs: a saved view reads `beacon` and `vector` only. Codex pages are
found through P6 search, which owns the page read path and its cascade-share semantics.

One obligation it does not state: a `readable`-scoped view is the first genuinely cross-space read
in the product, and therefore the first real consumer of §5's read-query shape. Read the warnings
recorded in §5 before writing that query — the shape published there was never implemented, and
taken literally it is both incorrect and unsafe.

**Query JSON — CORRECTED.** The shape below is NOT what shipped, and is kept only to show what
was rejected. It is a query language: it has a grammar, its field names come from the caller, and
every consumer needs an evaluator for it. ADR-0011's reasoning about arbitrary scripting applies
unchanged — a query you cannot reason about statically is one you cannot index, explain, bound or
migrate.

What shipped is a RECORD, not a tree: a closed set of named fields, AND-ed with each other and
OR-ed within themselves, with no `op`, no boolean nesting and no way for a caller to name a
column. The vocabulary is defined once, in `internal/core/views/filter.go`, which is also the
mapping target for the Jira importer ADR-0011 and ADR-0012 anticipate:

```json
{
  "v": 1,
  "filter": {
    "modules": ["beacon", "vector"],
    "space_ids": [], "statuses": [], "priorities": [],
    "assignees": ["me"], "kinds": [], "sprint_ids": [], "text": ""
  },
  "sort": { "field": "updated_at", "dir": "desc" }
}
```

`kinds` and `sprint_ids` are Vector-only and are REFUSED when Beacon is in the module set:
`tickets` has neither column, so such a filter can never match a ticket. Unknown fields are
refused with 422 (`VALIDATION_ERROR`), never stored and never dropped. ADR-0009 is unaffected — it
never specified this document's shape.

The rejected sketch follows.

**Query JSON (rejected sketch).** Versioned. Field names validated against a per-module whitelist;
unknown fields return 400 and are never interpolated.

```json
{
  "v": 1,
  "filters": [
    { "field": "status",   "op": "in", "value": ["open", "in_progress"] },
    { "field": "assignee", "op": "eq", "value": "me" }
  ],
  "sort":  [{ "field": "updated_at", "dir": "desc" }],
  "limit": 50
}
```

Ops: `eq`, `neq`, `in`, `not_in`, `gt`, `gte`, `lt`, `lte`, `contains`, `is_null`,
`is_not_null`. The literal `"me"` resolves server-side to the calling user, so a shared view
means the right thing for each viewer.

**Shipped in P5 as `042_dashboards.sql`.** The sketch below is retained as the record of what was

### Full-text search — number unassigned (was 027, now shipped as attachments)

PostgreSQL full-text using generated stored columns rather than triggers, so the index can
never drift from the row.

**Re-verified against the schema at migration 028.** Every object this sketch names to drop still
exists, under exactly these names, and nothing in migrations 015–028 touched any search vector,
index, function or trigger. P1.5's corrections survive intact. Two things it did not account for
are recorded below.

Column names are verified against the scaffold: `pages(title, content)`,
`tickets(title, description)`, `project_items(title, description)`. But **all three tables
already carry a `search_vector` column**, in two different states, and a plain
`ADD COLUMN` would fail on every one of them:

- **`pages.search_vector` already matches the target state.** `009_indexes.sql` created it
  `GENERATED ALWAYS AS` with exactly the weighted expression below (title `A`,
  content `B`), with GIN index `idx_pages_search (search_vector) WHERE deleted_at IS NULL`.
  This migration has nothing to do for pages.
- **`tickets.search_vector` and `project_items.search_vector` are trigger-maintained and
  unweighted.** `014_split_items_phase1.sql` created them as plain `TSVECTOR` columns
  updated by `update_tickets_search_vector()` / `update_project_items_search_vector()`
  triggers (`to_tsvector(title || ' ' || description)`, no weights), with partial GIN
  indexes `idx_tickets_search` / `idx_project_items_search`. This migration replaces that
  arrangement: drop the triggers, functions, columns, and indexes, then add the generated
  stored columns.
- The legacy items table also has a generated `search_vector` from `009`; it is not part of
  search and this migration does not touch it. **It is no longer called `items`** —
  `015_polymorphic_comments_relations.sql` renamed it to `items_archive`. PostgreSQL does not
  rename a table's indexes along with the table, so its GIN index is still called
  `idx_items_search` and now sits on `items_archive`. Do not assume `idx_items_search` refers to
  a live table, and do not assume the name `items` is free.
- **The sketch names only the `tickets` / `project_items` objects.** `idx_pages_search` and
  `idx_items_search` (both from `009_indexes.sql`) are generated-column indexes and are not named
  here at all. Any later attempt to unify all four tables onto one scheme must handle those two
  separately — a generated column cannot be converted by dropping a trigger, because there is no
  trigger.

```sql
-- +goose Up
-- pages.search_vector already exists in the target form (009_indexes.sql) — untouched.

DROP TRIGGER  tickets_search_vector_update ON tickets;
DROP FUNCTION update_tickets_search_vector();
DROP INDEX    idx_tickets_search;
ALTER TABLE   tickets DROP COLUMN search_vector;

ALTER TABLE tickets ADD COLUMN search_vector tsvector
    GENERATED ALWAYS AS (
        setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
        setweight(to_tsvector('english', coalesce(description, '')), 'B')
    ) STORED;

DROP TRIGGER  project_items_search_vector_update ON project_items;
DROP FUNCTION update_project_items_search_vector();
DROP INDEX    idx_project_items_search;
ALTER TABLE   project_items DROP COLUMN search_vector;

ALTER TABLE project_items ADD COLUMN search_vector tsvector
    GENERATED ALWAYS AS (
        setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
        setweight(to_tsvector('english', coalesce(description, '')), 'B')
    ) STORED;

CREATE INDEX idx_tickets_search       ON tickets       USING GIN (search_vector)
    WHERE deleted_at IS NULL;
CREATE INDEX idx_project_items_search ON project_items USING GIN (search_vector)
    WHERE deleted_at IS NULL;

-- +goose Down
-- Restores the exact 014 trigger-based arrangement on tickets/project_items
-- (unweighted trigger-maintained vectors and the same index names), so a
-- rollback returns the schema to the pre-search state. pages untouched.
```

The down migration must recreate the `014` trigger functions and columns verbatim — a down
that merely drops the generated columns would leave tickets and project_items with no
search vector at all, which is not the pre-search state.

## 5. Permission resolution

Resolve **once per request** in middleware, cache on the request context, and have every
query filter against the result. The cache lives for one request and is never shared across
requests — that is what makes revocation and expiry immediate.

```
readable_space_ids(user, org):
    if org_role(user, org) in ('admin', 'owner'):
        return all non-deleted space ids in org          # bypass, no rows

    effective_teams := SELECT id FROM teams
                       WHERE org_id = $org AND deleted_at IS NULL
                         AND path && $direct_team_ids     # GIN indexed, one query

    return  spaces where visibility = 'org'
          ∪ space_grants where subject_type='user' and subject_id = user
          ∪ space_grants where subject_type='team' and subject_id = ANY(effective_teams)
          # all three legs join spaces and require deleted_at IS NULL, so a
          # grant on a soft-deleted space never resolves
```

`path && $direct_team_ids` returns every team whose ancestor chain touches one of the user's
teams — exactly the user's teams plus all their descendants. One indexed query, no recursion
at request time. **Verified against P2's shipped `ResolveAccessRows`.**

Two corrections against what shipped: `owner` counts as an org admin for the bypass, not only
`admin`; and a teamless user must produce an empty array rather than NULL, or `path && NULL`
yields NULL and the whole leg silently disappears.

```
readable_entity_ids(user, org):
    shares := entity_shares
              where revoked_at IS NULL
                and (expires_at IS NULL or expires_at > now())
                and (audience = 'org'
                     or (audience = 'team' and audience_id = ANY(effective_teams)))

    direct   := entity_id for EVERY share, cascade or not
    subtrees := (entity_id, space_id, current path) for shares
                where cascade = true and entity_type = 'page'
    return (direct, subtrees)
```

**A cascade root belongs in `direct` as well as `subtrees`.** This document previously said
`direct := entity_id for shares where cascade = false`, which drops the shared root page's own
coverage on the floor — the subtree match covers descendants, not the root. P3 puts every share
row into `direct` regardless of `cascade` for exactly this reason.

The subtree rows carry the root's **current** `space_id` and path, re-read on every resolution.
Never snapshot them: a root that moves must cover its new subtree immediately and its old one
never.

### The cross-space read-query shape

**Read this before implementing it.** The shape below is *design for P4 saved views and P6
search*, not a description of running code. No shipped endpoint binds a readable set as a query
parameter: P3's shared reads resolve one already-identified entity, space-scoped routes 404 in
middleware, and the two existing multi-space reads — the space directory
(`GET /orgs/{org_id}/spaces`) and user-scoped notifications — filter in their handlers instead.
The version this document carried until now was never implemented and would not have been safe if
it had been.

```sql
WHERE space_id = ANY($readable_spaces)
   OR id       = ANY($shared_direct)      -- includes cascade roots themselves
   -- pages only: subtree membership is a prefix match on the materialized
   -- path. pages.path is dot-separated TEXT ("{root}.{parent}.{self}", from
   -- 012_pages_materialized_path.sql), NOT an array, so the match is against
   -- the shared root pages' path prefixes — not an && array overlap.
   --
   -- Each cascade root contributes a (space_id, pattern) PAIR, and the pair
   -- must stay bound together — hence the unnest of two parallel arrays into
   -- a row set rather than two independent ANY(...) terms. See point 3.
   OR EXISTS (
        SELECT 1
        FROM unnest($shared_subtree_space_ids::uuid[],
                    $shared_subtree_like_patterns::text[])
             AS root(space_id, pattern)
        WHERE pages.space_id = root.space_id
          AND pages.path     LIKE root.pattern
      )
```

Four things to get right, each of which is a defect if got wrong:

1. **The bound values are patterns, not paths.** A stored path is not a LIKE pattern. Each root
   path must become `EscapeLike(root) + '.%'` — escaping `\`, `%` and `_` first, because
   `pages.path` is unconstrained `TEXT` and a metacharacter that ever landed there must match
   itself rather than widen the pattern. Shipped code exposes this as `SubtreeLikePattern`.
2. **The pattern deliberately excludes the root.** `root + '.%'` matches strict descendants only.
   The root is covered by the `id = ANY($shared_direct)` term above — which is why the correction
   to `readable_entity_ids` is load-bearing rather than cosmetic.
3. **Subtree coverage must be pinned to the root's own space, per root.** `pages.path` uniqueness
   is not enforced across spaces — there is no unique constraint on it in any migration — so a
   path-prefix match that is not pinned can widen coverage across a space boundary. Every shipped
   subtree query pins `p.space_id`, and P3's in-process check skips any cascade root whose space
   differs from the candidate's. There is a regression test for the path-coincidence case.

   **The pin must be per-root, not per-query.** Two independent terms —
   `space_id = ANY($spaces) AND path LIKE ANY($patterns)` — look pinned and are not: they match
   the cartesian product, so a page in root A's space whose path sits under root B's subtree
   satisfies both halves. That is the same leak, reintroduced by a sketch that appears to fix it.
   Keep each `(space_id, pattern)` bound together, as the `unnest` above does.
4. **The exact-segment boundary.** A cascade on `a.b` covers `a.b.c` and must never cover the
   sibling `a.bc`. A naive `HasPrefix` or `LIKE root || '%'` matches both.

**One thing P6 must build first — not P4.** `SharedEntities` exposes `CascadeRootPaths()`, which
returns paths only: `cascadeRoot.spaceID` is unexported and no accessor reveals it, so
`$shared_subtree_space_ids` cannot be populated from the current API. Whichever phase queries
**pages** across spaces needs an accessor returning the `(space_id, pattern)` pairs together. Do
not work around it by binding paths alone; that is precisely the shape point 3 forbids.

This said "P4" until P4 shipped and found the premise did not hold. Saved views read `tickets` and
`project_items` only, and migration 026 constrains cascade to pages
(`entity_shares_cascade_pages_only`) — so a share on either of those tables is always exactly one
entity, and `DirectIDs(entityType)` is the complete story. P4's fan-outs therefore carry a direct-id
union and no subtree term at all, correctly. **P6 search reads pages and still needs the
accessor**; the gap is open and recorded as D46.

(The teams table's `path UUID[]` with `&&` in the resolution sketch above is unaffected —
that column is new in `022` and is designed as an array. Only the *pages* subtree match
uses the existing TEXT path.)

Effective capability on a space is the **highest** role across all matching grants.

**Where the resolved set is actually enforced.** "Have every query filter against the result"
describes the intent, not today's mechanism: no shipped query binds the readable set as a
parameter. Three mechanisms are in force, and an audit of read paths must cover all three:

- **Space-scoped routes** 404 in middleware via `RequireSpaceReadable`.
- **The space directory** (`GET /orgs/{org_id}/spaces`) is org-wide and filters per space in the
  handler with `CanReadSpace`, because it must show locked `discoverable` rows that a middleware
  404 would hide.
- **User-scoped routes** — notifications — filter on the caller's own identity and never consult
  the readable set at all. `notifications` carries no `space_id`, so a row's continued visibility
  after access is revoked is a question this section does not answer. Flagged, not resolved.

The bound-array shape becomes real with the first genuinely cross-space endpoint in P4. All of
these are legitimate; what is prohibited is the option below.

**Prohibited:** per-item authorisation queries inside a list handler. See test case 23.

**Share resolution is mounted per route family, not globally.** P3 resolves shares only on the
`/shared` subtree, deliberately, so space-scoped routes keep P2's per-request query budget
unchanged. P4 and P6 will need it on their cross-space routes too — mount it there explicitly and
re-run the case-23 constancy tracer, rather than moving it up to the org-wide middleware where
every route starts paying for it.

```
PATCH  /api/v1/orgs/{org_id}/dashboards/{dashboard_id}
DELETE /api/v1/orgs/{org_id}/dashboards/{dashboard_id}
PUT    /api/v1/orgs/{org_id}/dashboards/{dashboard_id}/gadgets
```

Gadget layout saves as a whole collection, never per gadget, to avoid partial states.

### Search

```
GET    /api/v1/orgs/{org_id}/search   ?q=&modules=&team_id=&space_id=&limit=
```

Two behaviours, served here, never conflated in the UI:

- **Scoped** — pass `space_id`. Fast, within one space.
- **Global** — omit `space_id`. Every readable space plus shared entities, tagged with module
  and owning team.

Scoped search UI offers one-click widening that preserves the query string.

Every endpoint requires swag annotations and `make docs` regeneration in the same PR. The
`docs-check` gate enforces it.

### Audit events

Written append-only for every mutation of a team, membership, grant, space visibility, space
owner team, or share. Action names follow `entity.verb`:

```
team.created  team.updated  team.reparented  team.deleted
team_member.added  team_member.removed
grant.created  grant.updated  grant.revoked
space.visibility_changed  space.owner_team_changed
share.created  share.revoked
```

## 8. Design tokens

### Module chips

The governing rule: **hue with matching text means state; hue with neutral text means
provenance.** Two channels that never collide.

```css
--module-beacon:     #E0806A;
--module-codex:      #A99BEE;
--module-vector:     #4A90D9;
--module-chip-alpha: 0.30;
--module-chip-fg:    #A6AEBC;
```

A module chip's background is its hue at 30% alpha; icon and text are `--module-chip-fg`.
**Never colour the chip text.** Doing so turns it into a status pill and destroys the
distinction.

Status and priority pills keep their existing behaviour — tinted background with matching
foreground.

### Existing system

Dark mode default. Steel blue `#4A90D9` for interactive and selected states. Dark slate
`#0F1117` page background. Inter for UI, JetBrains Mono for keys and code.

## 10. Non-negotiables

These override any instruction in a task prompt.

**Testing.** All of section 2. Real PostgreSQL via `internal/testutil.NewTestDB(t)`; no
mocks. Assertions are never weakened. Blast-radius review on every PR. No blank checkboxes.
DRAFT unless all three gates exit 0.

**Repository.** Agents perform **no git operations** — no commits, pushes, tags, or branch
changes. Agents **never create or edit the roadmap**. No agent-name file suffixes. Migration
numbering is immutable once shipped.

**Architecture.** `tickets` and `project_items` stay split. RS256 signing keys stay in the
database. Wire format is lowercase snake_case. Frontend network access goes through
`web/src/lib/api.ts` only. Org admin is a middleware bypass, never grant rows. Shares widen
only, never narrow. The audit log is append-only.

**Product.** No pricing, hosting-tier, or paywall language anywhere in code or docs.
Azimuthal is Apache 2.0, fully featured for every user, with no enterprise tier —
permanently.
